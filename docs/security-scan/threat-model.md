`kms` is a self-hosted parameter store and secret-management service delivered as one Go binary. It stores state in SQLite, exposes a machine-facing gRPC API and browser/admin HTTP API, embeds a statically exported Next.js UI, and ships Go and Python client SDKs. Its primary security purpose is to keep application secrets confidential at rest while enforcing namespace-scoped identity and authorization controls for live access. The primary runtime is `cmd/parameter-store` plus `internal/cli`, `internal/server`, `internal/core`, `internal/storage`, `internal/crypto`, `internal/ca`, `internal/policy`, and `internal/watch`. The `frontend` and both SDKs are also product surfaces because they handle credentials, plaintext secret values, namespace context, and update streams. Tests, plans, and generated protobuf bindings are supporting surfaces rather than independently deployed services.

The most valuable assets are secret plaintext, the KEK/master-key material, per-secret client-bound tokens, identity bearer tokens, private keys and certificates, the built-in CA private key, authorization policy, audit integrity, configuration-release integrity, and the availability and ordering of versioned configuration. Parameters are intentionally plaintext in SQLite but may still contain sensitive operational metadata. The SQLite database exposes identities, policy, audit, namespace, release, and schema metadata even when secret ciphertext remains protected.

# Threat Model, Trust Boundaries, and Assumptions

The principal external actors are application clients, browser administrators, platform operators, and attackers able to reach the HTTP or gRPC listeners. Application identities are either token-authenticated or certificate-authenticated and may be bound to a home namespace. Admin identities form a distinct management plane and intentionally bypass normal namespace policy and the per-namespace authentication-method gate; their credentials therefore carry broad authority. Operators control deployment configuration, server TLS material, KEK files or passphrases, database and backup files, reverse-proxy behavior, import/restore inputs, and the host itself. Developers control source, generated clients, build inputs, dependencies, and examples. These operator- and developer-controlled inputs are not normally attacker-controlled, but compromise of either control plane has large consequences.

The main trust boundaries are:

- Network clients to the HTTP and gRPC transports. Authorization metadata, bearer tokens, client certificates, secret access tokens, JSON/protobuf bodies, query parameters, resource names, pagination controls, and streaming state are untrusted until authenticated, validated, and authorized.
- Authentication to authorization. A resolved identity and authentication method must remain bound to the same request, namespace, certificate serial, and long-lived stream. Deny precedence, the implicit home-namespace read/list grant, namespace authentication-method restrictions, disabled identities, and certificate revocation must be enforced consistently across HTTP, gRPC, watch, and release paths.
- Browser UI to HTTP management API. The UI holds an admin bearer token and can reveal plaintext secrets, mutate policies and identities, activate releases, and issue certificates. A script or origin able to steal or misuse that token can exercise the same privileges. The design assumes bearer tokens are deliberately attached by the application rather than ambient cookies, which lowers classic CSRF risk but makes XSS and token exfiltration especially important.
- Server process to SQLite. Secret plaintext must be encrypted before persistence; ciphertext must remain bound to `(env, app, key, version)` and cryptographic layer by authenticated associated data. Reads must not confuse versions, namespaces, wrapping modes, KEK IDs, or client-bound state. Transactions must preserve version, release, rotation, and changelog invariants under concurrency and crash recovery.
- Server process to KEK and CA key material. A key file or passphrase-derived KEK is trusted only after the key-check canary succeeds. KEKs should remain outside SQLite; CA and DEK wrapping must use domain-separated authenticated encryption. The design explicitly does not defend against arbitrary code execution in the live server process, because such an attacker can read keys, plaintext, and credentials from memory.
- Server to filesystem and operational tooling. Database, backup, restore, migration, certificate-output, configuration, and key-file paths are operator-controlled. Commands must avoid unsafe overwrite, symlink, permission, archive, and partial-failure behavior. Backups contain ciphertext plus sensitive metadata and remain valuable targets.
- Watch/release producer to consuming SDK. Revisions, snapshots, aliases, schemas, and notifications must be namespace-bound, ordered, fenced, and reauthorized. Secret values should never appear in watch events; clients must not accept stale or cross-namespace state after reconnect, token revocation, certificate revocation, release supersession, or partial resolution.
- Reverse proxy to server. `X-Forwarded-For` is trustworthy only when `security.trust_proxy_headers` is enabled behind a proxy that overwrites it. Otherwise it can be used to evade IP-keyed throttling and forge audit source addresses. Transport confidentiality and authentic server identity depend on TLS being enabled or supplied by a correctly configured trusted proxy.

Attacker-controlled inputs include all remotely supplied headers and metadata, bearer and per-secret tokens, client certificates, HTTP paths and query strings, JSON/protobuf fields, secret and parameter bytes, schema documents, namespace labels, keys, policy names and rule fields available to an authorized writer, release definitions, watch cursors/revisions, and concurrency/timing. Credential material that an attacker has stolen is attacker-controlled even if syntactically valid. The database file, backup, server config, KEK file, passphrase, TLS files, import content, and CLI output paths are operator-controlled under the normal deployment model; vulnerabilities requiring malicious control of those inputs generally have lower remote severity unless a realistic lower-privilege boundary exists.

Security invariants include: unauthenticated methods remain narrowly limited to health and the public CA; all other requests authenticate and check readiness; authorization evaluates the exact operation and namespace with deny precedence; admin-only actions cannot be reached by client identities; namespace authentication-method restrictions cannot be bypassed by switching transports or credentials; secrets never reach SQLite, logs, audit records, metrics, watch events, release documents, or normal error strings in plaintext; every secret version uses authenticated encryption with correct AAD and fresh key/nonce material; client-bound values require the independent client token; secret reads fail closed when their audit write fails; destroyed versions cannot be recovered; KEK rotation leaves no live record dependent on a retired key and does not expose plaintext; long-lived streams continuously revalidate identity and certificate state; changelog revisions do not repeat or cross namespaces; configuration releases resolve atomically and stale preparation cannot overwrite newer state; and sensitive credentials are returned only through deliberate one-time flows.

# Attack Surface, Mitigations, and Attacker Stories

The HTTP API in `internal/server/httpserver` and gRPC services in `internal/server/grpcserver` are the largest remote attack surfaces. Relevant classes include authentication confusion, authorization bypass, namespace/object confusion, policy wildcard errors, admin/client privilege escalation, missing method gates, information disclosure through listing or errors, credential brute force, request-size denial of service, unsafe proxy trust, and stream reauthorization gaps. Existing controls include centralized transport authentication, core-layer authorization, verified-chain checks for mTLS, generic authentication failures, bounded HTTP bodies, login throttling, request IDs, readiness gates, panic recovery on gRPC, and explicit public-method allowlists.

The cryptographic surface in `internal/crypto`, `internal/core`, `internal/ca`, and key rotation/unseal flows is exposed indirectly through secret writes/reads, client-bound tokens, database corruption or theft, initialization, and rotation. Relevant failures are nonce/key reuse, incorrect AAD, layer confusion, weak token derivation or comparison, ciphertext/version swapping, downgrade from client-bound to normal mode, use-after-destroy, wrong-key acceptance, incomplete rewrap, secret retention, and error-oracle behavior. Existing controls include AES-256-GCM only, a fresh DEK per version, layer-specific AAD suffixes, HKDF for client-bound keys, a key-check canary, zeroing of primary buffers, explicit wrapping modes, transactional storage, and encrypted CA private keys.

SQLite and operational code are exposed to attacker-created resource data and operator-created file paths, databases, backups, restores, and migrations. Remote SQL injection should be unlikely because GORM/query parameterization is used, but dynamic query fragments, pagination/order controls, table-selection logic, and raw SQL deserve review. Concurrency and transaction bugs can become security bugs if they cross namespaces, reuse versions/revisions, lose deny/audit updates, revive destroyed data, or activate partially validated releases. File operations must be reviewed for unsafe permissions, symlinks, accidental overwrite, and secret-bearing reports.

The admin UI and SDKs are security-relevant clients. Frontend XSS, unsafe HTML rendering, URL-based secret leakage, persistence of admin tokens in vulnerable browser storage, or accidental caching can yield management-plane compromise. SDK namespace parsing, TLS defaults, secret redaction, environment-variable precedence, caches, watch retries, and error rendering can disclose credentials or accept wrong-namespace/stale values. Insecure/plaintext client modes are intentional development features and become reportable when they are silently selected or contradict documented secure defaults, not merely because an operator explicitly requests them.

Realistic attacker stories include: a network attacker with a stolen low-privilege token attempts cross-namespace secret access or policy escalation; a malicious namespace member exploits implicit grants, listing, release, or watch behavior to read another tenant; an unauthenticated attacker brute-forces tokens or exhausts body/stream/database resources; a database thief swaps ciphertext or metadata to bypass client binding; a browser attacker uses XSS to steal an admin token and reveal secrets; a revoked identity keeps a long-lived stream alive; a proxy/header misconfiguration lets a remote client evade throttling or corrupt audit attribution; or concurrent operations violate rotation, destruction, version, or release fencing.

Out-of-scope or assumption-dependent stories include an attacker who already has arbitrary code execution as the service OS user, full control of both the database and live KEK plus process memory, a deliberately malicious administrator with intended full management access, or a developer who can ship arbitrary replacement binaries. These are deployment or supply-chain compromises unless the repository exposes an additional meaningful boundary, such as client-bound data that should remain unavailable even to a server operator with the database and KEK. Physical memory extraction, Go runtime copies that survive best-effort zeroing, and denial of service through total host resource exhaustion are also outside the primary guarantees.

# Severity Calibration (Critical, High, Medium, Low)

Critical issues enable unauthenticated or low-privilege recovery of broad secret plaintext, remote code execution in the server, compromise of KEK or CA private keys through a normal network path, or systemic bypass of tenant/admin boundaries. Examples include an unauthenticated API that dumps decrypted secrets; an authorization flaw that lets any namespace identity mint an admin credential or rotate keys; or a cryptographic/version-binding error that makes the full secret store decryptable from SQLite alone.

High issues expose a meaningful set of secrets or privileged operations across a strong boundary, permit persistent admin takeover, defeat client-bound protection under its stated database-plus-KEK attacker model, or allow remote integrity compromise of active configuration. Examples include cross-namespace secret reads with an ordinary client token; stored XSS reachable in the admin UI that steals the admin token; certificate mapping that authenticates the wrong identity; or stale release/watch logic that lets a remote writer reliably substitute attacker-chosen production configuration.

Medium issues require a valid but limited credential, narrow deployment conditions, or produce bounded disclosure/integrity/availability impact. Examples include leaking secret names or sensitive metadata from another namespace; a revoked credential remaining effective only for an existing stream for a bounded interval; proxy-header trust that defeats throttling when an unsafe documented option is enabled; or a remotely triggerable, recoverable server crash without plaintext disclosure.

Low issues have minor or highly constrained impact, require trusted operator/developer control, or are defense-in-depth gaps without a demonstrated boundary crossing. Examples include imprecise audit source attribution behind a misconfigured proxy, overly detailed non-secret validation errors, permissive permissions on a deliberately operator-selected non-secret output, or a missing hardening header with no executable injection primitive. Findings that merely restate documented plaintext development defaults, require a malicious full administrator, or assume arbitrary server-host code execution should normally be informational or suppressed unless they break an independent stated guarantee.
